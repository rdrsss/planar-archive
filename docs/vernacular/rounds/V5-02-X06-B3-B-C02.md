#### Decisions

**R2 fixture design (route consumption).** Test `X06 B3 B exhaustion depends on route
consumption because the instruction budget is one cumulative counter`. The fixture is the
default body plus one custom job (`for i=1,N do n=n+1 end` in the custom shape). The
calibration recorded in the test (Debug) is: route (`marks[1]-marks[0]`) costs 9000
instructions independent of N; validation plus preparation (`marks[3]-marks[2]`) costs
`121000 + 2*N` (measured at N = 1000, 1e6 and 2e6: 123000, 2121000, 4121000). The heavy
variant uses `N = 49937000`, so validation alone is 99995000 (below the 100000000 budget)
while route plus validation is 100004000 (above it); only a budget that carries the route's
consumption into validation can exhaust. The light variant uses `N = 49927000` and must
succeed: the test checks `route > 0`, `instructions < budget` and `valid < budget`, derives
the heavy validation cost from the light measurement (`valid + 2*(heavy_n - light_n)`),
checks it is below the budget and that adding the route cost exceeds it, then requires the
heavy variant to refuse with `resource_limit`, limit `instructions`, maximum 100000000, not
semantic, with `before.instructions` below the budget. Each phase alone stays under 100M.
Reviewer mutant `d9b54d0579c3` (`reset-f-instr`, `s.instructions = 0;` after `mark(2)`) is
killed by this test (failing assertions at scratch-copy lines 2002 and 2008, 1 failed of
36). The same test also kills `reset-a-instr`, `reset-e-instr` and `double-charge-route`.

**R3 watch fixes.** The read-count interposer holds one inode and resets its counter on
each `watch_path`, so a zero-read assertion watching the declaration and then the registry
checked only the registry. Fixed sites (the brief's 1528, 1637, 1834 are 1529, 1638 and
1846 in the current file): the `into_extension` adoption test watches the declaration
(1529); the phase-2 success test now watches the declaration alone and asserts zero reads,
then watches the registry alone and asserts zero reads (1638 and 1641); the capture-change
test watches the declaration alone before `prepare_load` (1846). Positive control: new test
`X06 B3 B prepare_load reads the declaration through the watched interposer` watches the
declaration on a successful `prepare_load` and requires `planar_admission_read_attempts() > 0`
(the C01 reviewer measured 10). Mutants that read the declaration in `prepare_load` or in
`observe` are killed by the zero-read assertions (`decl-read-in-prepare`: two tests;
`decl-read-in-observe`: the phase-2 test), and the test-side mutant that watches an unread
file (`control-watches-unread-file`) fails the positive control.

**R3 rename.** Old name (introduced in C01, so renaming is allowed): `X06 B3 B captured
profile content is reverified before source binding, after capture and after sealing`. New
name: `X06 B3 B prepare_load reverifies captured profile content exactly three times`.
Reason: the order of the three verifications is not observable from the public surface;
the test pins the count (three verifications, two reads each, so `6` reads of the module),
and mutant `52b29026261a` (`reverify-moved`: the pre-capture verify removed and one added
after source capture, same total count) survives with 0 failed of 36, so the old name
claimed an ordering the test cannot check. The test comment now says so. Removal of any one
verify, or all, is killed by the count (`reverify-pre`, `-mid`, `-final`, `-mid-final`,
`-all`, `-all-and-source`, all at the `== 6` assertion).

**Masking reason (why the capture_changed test cannot catch removal of the pre-capture
verify).** The native `read_file` verifies its receipt (`r.authority->verify(fd)`) before
any read, so with the explicit pre-capture verify removed, `open_bound` refuses first
(`capture_changed`, field `profile`, zero declaration reads, `cleanup_ran` stays false),
which is the same observable outcome. Only the six-read count pins that verify (`4 == 6`
when it is removed). Probe evidence: removing the verify alone (`reverify-pre`) is killed
only by the count test; `open-bound-refusal-protocol` and `source-error-mapping` alone
survive because the pre-capture verify refuses before the mutated branch is reached; the
combinations `reverify-pre-and-open-bound-protocol` and `reverify-pre-and-source-error-mapping`
are killed by both capture_changed tests and the count test, which shows those assertions
can fail once the masking verify is also gone.
