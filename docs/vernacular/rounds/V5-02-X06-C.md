### Objective

Deliver the "Native profile transactions" row of the
[bounded delivery sequence](../profile-preparation-architecture.md#bounded-delivery-sequence-and-independent-gates):
a ledger acceptance overload with a private adapter that consumes the opaque `prepared_profile` produced by B3-C and
completes it atomically through the same common transaction algorithm the embedded `complete_acceptance` uses.
The adapter must preserve, in the existing order: exact replay and conflict before candidate inspection and CAS, format
version check, error vocabulary, completion receipt phases and commit uncertainty, and all embedded behaviour.

Out of scope: no `init` or envelope cutover, no public CLI change, no whole-invocation budgets (X06-D), no change to
how a prepared profile is built. The fresh profile acceptance refusal at the public surface stays; only this internal
overload may accept a `prepared_profile`. Nothing accepts caller-built data as authority.

Required evidence beyond ordinary tests: original native receipt races (the sealed source capture and the profile
capture changing before commit, each checked at the precommit boundary after the transaction rows are staged) and proof
that no Lua runs while the write lock is held.

### Carried item 1 settled from the contracts: the moved-from message

`prepared_profile::verify_native_receipts` returns `capture_changed` / "Captured inputs changed." for a moved-from owner
and for a source mismatch that is not a capture error. That text is not in the closed table in
[external-profile-contract.md](../external-profile-contract.md) (X-LIMIT, "New native sites"), and ledger completion
now consumes the method. No new message is needed, for these reasons:

1. The completion path never surfaces the method's diagnostic message. The embedded overload turns any failed
   `candidate.verify()` into `format_error{capture_changed, "Capture changed before acceptance commit"}`
   (`src/engine/ledger/acceptance.cpp`), and the public mapping in `src/cmd/planar/response.cpp` replaces every
   `capture_changed` format error with the fixed text "Captured declaration inputs changed", which is the row
   "selected receipt changed" in the native failure table of
   [load-command-contract.md](../load-command-contract.md). The new adapter reuses that same mapping, so the diagnostic
   text is internal, as it already is for the embedded `prepared_acceptance::verify` ("Captured inputs changed.",
   `src/engine/acceptance/prepared.cpp`).
2. The ledger contract (step 5 and the paragraph after it) fixes the code: a detected receipt change refuses
   `capture_changed` before commit. The external-profile contract (X-ROOT/seal text near "with all acceptance receipts
   immediately before load commit under lock") says the same. Neither fixes message text for a moved-from owner, and a
   moved-from owner is a protocol misuse that the adapter must refuse before opening a transaction as
   `invalid_argument` / "Unavailable prepared acceptance", matching the embedded overload's moved-from refusal.
   **Corrected (X06C-R4, by C01 sync):** the sentence above was wrong about the order. As implemented and tested, a moved-from
   prepared profile is refused inside the write transaction, after the exact replay lookup, the format check and the head CAS
   and before any row is written (`profile_candidate::values()`; test "X06 C profile completion moved-from profile refuses after CAS
   before any row"). That is required: a moved-from profile must still replay (criterion 2) and candidate inspection happens only
   after CAS ([architecture](../profile-preparation-architecture.md) steps 1 and 2). Only a moved-from or in-use completion
   *receipt* (criterion 7, a different object) is refused before a transaction opens.
3. Therefore the method and its pinned test (`runtime.t.cpp`, "Captured inputs changed.") stay byte-identical, and the
   adapter must not forward the diagnostic text into a public error. A test must prove the public-facing format error is
   the existing one for both a source-receipt and a profile-receipt failure. No halt is needed; this is recorded as
   resolved. If search finds that any clause demands the profile-receipt text "Captured external profile changed" at the
   completion boundary, it must report that as a halt-worthy conflict rather than choose.

### Acceptance criteria (the search invariant table must give each a row, mutant and killing test)

1. Positive: a real prepared profile (built-in and custom job mix) completes into a v2 ledger: the stored source tree,
   registry, effective stdlib, interpretation and versions come from `profile_acceptance_data`, the request body is the
   exact `request_v2` of the bound intent (profile selector included), and the result bytes equal what a replay returns.
   An unchanged second request is `noop`; a changed profile creates a new revision.
2. Replay and conflict order, unchanged: equal request ID and body returns the saved bytes before any candidate
   inspection, before CAS and without running receipt verification; a different body with the same ID is
   `request_conflict` before CAS; a replay needs no live capture (inputs may be deleted); a moved-from prepared profile
   still replays. Replay sets phase `replayed` and the saved owner before the API copy.
3. Format order: a v1 ledger with a profile intent and a v2 ledger with a legacy intent refuse `unsupported_version`
   after an unknown request lookup and before the head read; the existing "Unsupported profile acceptance" refusal stays
   for the embedded overload when a profile argument is present, and is not reachable by the new overload's success path.
4. CAS: a stale expected head refuses `revision_conflict` with the existing details, with no row surviving; two different
   request IDs racing from the same head have exactly one winner.
5. Receipts: both retained receipt sets (source capture then profile capture, per
   `prepared_profile::verify_native_receipts`) are verified after rows are staged and `verify_before_commit`, immediately
   before COMMIT, never earlier and never skipped; a change to a closure file, mode or identity, to the profile or a
   module, or a change that occurs between staging and COMMIT refuses `capture_changed` ("Capture changed before
   acceptance commit" at the ledger boundary) with the transaction rolled back and no request row.
6. No Lua under lock: no Lua chunk, handler, receipt callback or conversion runs while the write transaction is open;
   the adapter takes only native, already-derived data. Evidence must observe this (for example the VM instruction or
   registration counter and a Lua side effect marker unchanged across the transaction) rather than assert it in prose.
7. Uncertainty and receipt: `completion_receipt` phases `committed`, `replayed`, `commit_uncertain` and the confirmed
   non-commit reset behave exactly as the embedded overload for every existing native fault case (abort, metadata fault,
   collision, atomicity, commit uncertain, transport); a moved-from or in-use *completion receipt* refuses `invalid_argument` before a
   transaction, and the saved bytes survive an exception. (A moved-from *prepared profile* is a different case: refused inside
   the transaction after replay, format and CAS and before any row; see "Carried item 1" point 2, corrected.)
8. One common transaction implementation: the embedded and profile paths share the staging, CAS, noop and append code;
   no copy of the algorithm. Embedded behaviour and all existing `complete_acceptance` tests pass unchanged.
9. Authority: no API constructs or accepts a prepared profile, `profile_acceptance_data` or a receipt from a caller; no
   raw handle or callback escapes; the new surface is not exported past what the adapter needs; compile and public
   surface audit shows no new construction path.
10. Moved-from message item (see above): the public error is the existing mapped one; the method text is unchanged.
11. Dependency audit: no target cycle; every generated test variant builds; `runtime` gains no import of
    `ledger.acceptance` or `ledger.storage`.

Carried limits, unchanged unless this round measures them: P01 masked, N1 phase coverage unmeasured, test #531 about
15.4 s of 30 s (do not slow it), macOS Debug only, Linux acceptance not run, fresh profile acceptance still refuses at
the public surface.
