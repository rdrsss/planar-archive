### Objective

This is the first scoped corrective round after R19. It takes the carried items that need no product-direction choice, in priority order, and is split because one review cannot hold all three.

Slice A (this round, R20-CARRY-A):

1. Make the two load-sensitive Debug tests robust under load without weakening what they assert. The roadmap names them by ctest number (#1321 and #1030), but ctest numbers shift as tests are added. The numbers refer to the R15-B era inventory (1,610 tests), where they were:
   - #1030: `recorded effective history selects wider fixed tree profile for valid closure above4096 files` (`src/engine/ledger/history_verification.t.cpp`, about line 1325). It timed out at 30.05 s under host load about 74 and passed at 13.43 s and 15.19 s on rerun. It takes 9 to 12 s on an idle host in Debug.
   - #1321: `v2 every native allocation failure remains a redacted typed resource refusal` (`src/engine/history/interpretation_v2_codec.t.cpp`, about line 495). It takes about 18 s on an idle host in Debug against the 30 s per-test limit.
   The later numbers #1030 and #1321 in the current 1,854-test inventory are different, fast tests and must not be edited. The coder first re-measures the slowest current Debug tests (the R19-ACCEPT-A-C01 run2 gate log under `tests/native/r19-accept-a-c01-evidence/raw/run2/04-gate-debug.log` lists the unusually slow ones, for example #243, #442, #458, #586, #1270 and #1272) and records which tests sit nearest their limit. The fix may be: a per-target `TEST_TIMEOUT` raised through `cmake/rewrite.cmake` and the owning module's `CMakeLists.txt` (the default limit is 30 s and other modules already use 60 or 120 s), or a reduction in the work the test does that provably keeps every assertion and every distinct code path. It must not lower the number of allocation points swept, remove an assertion, loosen a check, or hide a failure with a retry. The preferred outcome is the smallest change that gives at least a four times margin over the idle Debug time, with the reasoning recorded.
   Red-first: if a deterministic failure can be shown (for example running the unchanged test with the old limit under a controlled slowdown of the same factor as the observed load, or a count-based measurement of the work sweep), show it with the exact command and a hash of the pre-fix snapshot. If no deterministic red is possible for a pure timeout-property change, record that explicitly with the measurement evidence (idle time, loaded time, new limit) rather than inventing a red.
2. Configure timestamp follow-up. The B1 generator (`tests/native/v5-02-b1-support/generate.py`) and the D6 generators (`tests/native/r14-d6-support/generate.py`, and `tests/native/r14-d6-c01-support/generate.py`) use `Path.write_text` unconditionally, so every explicit configure rewrites unchanged generated files and invalidates native targets. Search for any other `execute_process` generator in `src/engine/runtime/CMakeLists.txt` and `src/cmd/planar/CMakeLists.txt` with the same defect and fix the ones that are equally unconditional (CMake `file(CONFIGURE)` already leaves identical content untouched). The fix is write-only-if-different, matching what `tests/native/r19-authoring-c01-support/generate.py` already does. Add a test, registered so that it actually runs in the gate (a Python support test run by the gate driver or a CMake-script test; the coder decides and states how it runs and its count), that shows: a configure over an unchanged tree leaves the generated fixture files' mtimes unchanged, and the following build reports zero work (`ninja: no work to do.`). It must also show that a genuine content change still rewrites the file, so the test can fail in both directions.
