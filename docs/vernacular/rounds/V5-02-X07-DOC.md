### Objective

Write the architecture addendum X07 needs, so that X07 search, coders and reviewer have no design choice left to make
alone. It must contain at least these parts.

1. **Closed factory over the five shipped families (Q1 B, D7-1, D7-2).** The factory's shape and where it lives in
   `planar.engine.runtime`; its admission (the per-family known-slot table from X-CAP: render workspace root, selected
   declaration, registry, source root, base root and observations file; load's existing set; init's ledger target
   and its relation to the trusted root; history's ledger alias; export's ledger alias and target-tree overlap;
   selected help as trusted capture only); the family registry (how the five-member `command_options` variant is
   closed, what a sixth member would require, and why there is no generic service factory); the dispatch of each
   family under a profile and how this satisfies X-CLI step 8 and the command contract's shipped-handler substitution
   requirement (name the substitute evidence: retained phase callables and the custom-shape effect on W and render
   output); and the relationship to `open_opaque`, `into_extension` and the creation-site audit (D7-12). It must say
   how X07-A (CLI11 envelope, probes, final parser, help, error adapter, envelope module placement per D7-4) and
   X07-B (extension handler module, load and replay wiring, format2 init and codec selection per D7-6, races and
   faults per Q3, budget threading per Q2) attach to it, and which wave owns each attachment (D7-13). It must state
   the factory's ownership boundaries (what it owns, what it must not expose) in the same terms as the existing
   constructor protocol, and give the revised wording for the architecture sentence "Other known shipped families
   require their own finite admission path; this document does not open them through a generic service factory".
2. **X01 production outcome table (D7-3).** One row per X01 argv row (all 44 envelope rows and all 12 opaque-probe
   rows from the spike), giving the production exit code, the precedence class (syntax guard, prefix usage, probe
   usage, profile error, final usage, late overlap, handler), whether the profile is accessed, and the governing
   X-CLI clause. Spike labels such as `final:ExtrasError` are translated, not copied. The verb-as-value row changes
   class (probe refusal before profile access, per X-CLI step 3) and the addendum says so explicitly. Alongside it, a
   production outcome and diagnostic table (D7-7): every production outcome and diagnostic class (registration
   error, extension preparation failure usage, protocol and resource, profile preparation error semantic, ledger
   format error, early-replay results, recovery fallbacks) mapped to exit code and response envelope, checked against
   the closed message table and X-LIMIT table of the external-profile contract. No new public code or message may
   appear; the table cites the existing message for each row.
3. **Other pre-X07 documentation the design assigns:** D7-2 (per-family known slots), D7-4 (envelope module
   placement and ownership list), D7-5 (observing that external Lua did not run, without hooks), D7-6 (request codec
   by opened ledger format), D7-8 (which stages charge the factory budget owner and which are inherited own-bound
   stages; this is Q2 A), D7-9 (Q3 A variants and the one real race), D7-10 (test placement), D7-11 (test-name
   preservation with a list of existing tests whose assertions the cutover will change, if the author can identify
   them without running anything), D7-12 (source-scan test) and D7-13 (wave order). Each appears as a decisions table
   row marked contract-decided (with citation), decided in the design or by operator decision, or new.
4. **Carried limits CL-1 to CL-6** (roadmap Next work). A short section stating, for each limit, whether X07 touches
   its code path and how X07 stays compatible: CL-1 (`call_retained_projection`, reachable through projection
   calls that X07 exposes via the extension handler) and CL-4 (`validate_profile_phases`, reachable through public
   profile calls) are the ones X07 may make more reachable; CL-2, CL-3, CL-5 and CL-6 as the roadmap classifies them.
   The addendum must not repair, reclassify or change any limit, and must say that X07 does not repair them. The
   section also lists the other carried limits (P01, N1, #531 timing, red snapshot tracked-only, Linux not run, ceiling
   pins) as they relate to X07's gate and brief.
5. **X07 brief inputs.** A short list of the standing pre-emptions P1 to P12 that X07's brief must carry, the
   clause-30 narrowing risk, the root-help-unchanged rule, and the recommended X07 round shape from the design
   (one addendum run, then one code round of two waves; split before coding if the candidate would be too large).

Out of scope: any product source, test, CMake or script edit; any change to an exact contract (see Halt rule); any
decision of a question the design leaves to the operator; repairing a carried limit; the X08, RA01 and R15 to R19

governing source, and edits nothing that depends on it. Known uncertain points the author must check against X-CAP

scratch CLI suites" as evidence placement. A confirmed reading is recorded with its citation; an unconfirmed one halts.
