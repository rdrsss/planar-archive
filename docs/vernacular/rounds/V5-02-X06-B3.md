### B3-A scope

1. Classes `profile_invocation` (copy deleted, no public default constructor,
   private constructor taking its own unique implementation, move transfers
   stable implementation addresses and counters, moved-from operations refuse),
   declared and implemented in `planar.engine.runtime`. `prepared_profile` is not
   introduced in this sub-round (no staged round references an unintroduced type);
   `prepare_load` is not declared.
2. `open_known_load(request_intent, ledger_path)`: requires codec2 profile intent,
   extracts the profile selector itself, captures profile and ordered modules once,
   metadata-admits the supplied workspace root and the selected workspace
   declaration file (declaration role), the registry file and the ledger selection
   before external registration, registers shipped and external chunks once in its
   private `command_vm`, then reverifies the original receipts. It reads no source
   content. It uses the B2 `source_capture` module's bound path for the root,
   declaration and registry receipts; it retains both root and declaration tokens
   in the same owner.
3. `open_opaque(profile_selector)`: captures and registers once with no untrusted
   input bytes; it can never prepare built-in load.
4. `catalog()`: immutable sealed final parser metadata borrowed from the owner.
5. `into_extension() &&`: a private same-runtime adoption constructor transferring
   profile capture, `command_vm` and counters into `extension_invocation`. No
   reverse conversion and no mutable `command_vm` extraction. Every actual
   `extension_invocation` creation site is audited and listed in the evidence.
6. The private active-frame refactor: split phase execution in
   `validate_profile_impl` from invocation entry so a same-module frame reference
   can be passed through later route, F, check and finalize calls without
   `begin_invocation` or counter reset. Public validation APIs keep their entry
   semantics and cannot supply the private frame. B3-A proves this with tests that
   the public paths are unchanged and that the owner opens exactly one frame; the
   cumulative-exhaustion test across phase 8, all jobs and preparation lands in
   B3-B, where those phases run.
7. Carried advisories, each resolved here or recorded with a reason:
   - **X06B2C01-N1:** the missing-declaration adapter (`known_declaration_error`)
     must detect absence specifically (for example at admission, or by checking
     for ENOENT) so that macOS `O_EVTONLY` EACCES on an unreadable declaration is
     not reported as missing; if that cannot be done without an admission change,
     document the macOS difference at the adapter and in the evidence.
   - **X06B2C01-N2:** the factory checks the receipt roles (workspace root,
     declaration, registry) explicitly.
   - **X06B2C01-N3:** a moved-from receipt returns `invalid_state`; poisoned and
     foreign receipts keep `capture_changed`. If search shows a different split is
     needed, record it.
   - The roadmap's note that the known-load row also applies
     `known_declaration_error` is satisfied by item 2.

### Acceptance criteria

1. Known construction metadata-admits root, selected declaration, registry and
   ledger before any external chunk executes; a test shows module and declaration
   hard-link refusal and that no source content was read.
2. Opaque construction cannot reach built-in load preparation (no such API).
3. Owner semantics: copy deleted, move preserves addresses and counters, moved-from
   refusal, consumed or failed owner publishes nothing, `into_extension` adoption
   keeps the original capture, VM and counters, and no second capture or
   registration happens.
4. One active frame per owner, with public validation entry semantics unchanged;
   existing runtime, shape and registration tests keep their names and pass.
5. Receipt-role checks and the N1 and N3 resolution have direct tests; any
   red-first regression is demonstrated before the fix and kept in evidence.
6. Existing fresh profile acceptance refusal remains; no public CLI change; the
   dependency audit shows no target cycle and no runtime-to-ledger-acceptance edge.
7. Coders add no `assert()` for required validation, use `std::expected` typed
   failures, and follow the module documentation rules.
