## Addendum (added at the approval step, X07-C01-R3): two recorded limits of the probe

- D5/D10 side effect: SQLite's `unixCheckReservedLock` (`F_GETLK` with `F_WRLCK`, `vendor/sqlite/b9c7/sqlite3.c:41894-41904`) reports our probe's read lock on the RESERVED byte as a RESERVED holder. For the microseconds the probe is held, another process that checks reservation treats any journal as live. No refusal results; a competing check only excuses a journal for that interval.
- D11 condition: the unlock is safe only if this process holds no RESERVED lock on the same inode, because POSIX lock replacement would drop it. No current product caller reaches the probe in that state (traced: the probe runs before the connection opens and after the read snapshot is released). A future caller that holds a write transaction on the same ledger in the same process must not use the probe.
