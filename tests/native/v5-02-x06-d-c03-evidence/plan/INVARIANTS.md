### Equivalence arguments (source readings; the prober applies every mutant)

Fact F, QUALIFIED (gap 5). On a `protected_call` return (curated `pcall`, `runtime.cpp:119-138`) trusted Lua never continues after an exhaustion flag: it
re-raises when `instructions >= instruction_limit`, `exhausted`, `lua_memory_failed`, `stack_exhausted`, `native_memory_failed` or `conversion_failure` is set
(`stdlib/planar/README.md:50-58`). F does NOT hold for (a) untrusted profile Lua after a RECOVERED allocator refusal: `allocate` sets `s.exhausted` on any
refusal (`runtime.cpp:98-100`), Lua's emergency GC retries (`vendor/lua/0b10/src/lmem.c:162-182`), nothing resets `s.exhausted` and the instruction hook does
not test it, so the shape keeps running; (b) an allocation refusal while a native error is being raised. Arguments E2, E3, E3b and E5 therefore do NOT rest on
F. They rest on: no profile code runs on those paths, and no native that runs there records a non-resource `bridge_error`.

- **E1 (site 1, X4): WITHDRAWN.** Revision 1 called X4 equivalent. It is not: after a recovered refusal, `register_external` throws `external_protocol` whenever
  `exhausted(context(l))` is true (`runtime.cpp:1260-1261`), `command_failure` runs, and with X4 the guard no longer blocks `bridge_error`. The direct shape
  site then returns the protocol failure (`bridge_error` first, `runtime.cpp:4382-4383`) instead of `command_resource` (`Lua allocation exceeded`), and
  `call_retained_value` (site 2, `runtime.cpp:2071-2074`) does the same. Killed by C3-9e. Note the expected result: the allocation refusal occurred first, so it is
  the first terminal failure (clause 396); the illegal registration came later.
- **E2 (X2).** `shape_failure` is only set inside the `failure` lambdas of `resolve_shape_definition_impl`, `invoke_shape_impl`, `invoke_projection` and
  `validate_profile_phases` (for example `runtime.cpp:3701-3711`, `4270-4276`), and each lambda returns `*shape_failure` itself on the next call.
  `prepare_load` hands `prepared.error()` from `validate_profile_phases` to `refuse` (`runtime.cpp:5431`) and refuses at once, so `fail()`
  (`runtime.cpp:5127-5134`) receives a diagnostic that already equals `shape_failure`. No later failure source runs after a shape failure. Independent of F.
- **E3 (site 3, M_O3).** The only caller of `call_retained_assembly` is the extension projection callback (`runtime.cpp:6403`), which returns early when
  `exhausted(s)` or `c.bridge_error` is already set (`runtime.cpp:6301`). The callee is the trusted `assemble_projection_material` (`stdlib/planar/render.lua:61`)
  on plain data: it calls no profile function and no registration or command-service native (the only `pcall` uses in the stdlib are `observations.lua:11`,
  `bootstrap.lua:12`, `schema.lua:305`, each wrapping the pure-Lua `json_parse`). `bridge_error` is empty on entry and nothing in the call records one
  (`command_failure` is reachable only from command natives), so the `bridge_error` branch is never taken whichever order the two checks have. Independent of F.
- **E5 (site 5, M_O5), rebuilt (gap 3).** In `prepare_load` the route call (`call_retained_value`, `runtime.cpp:5404`; checks at `5405-5408`) runs BEFORE `validate_profile_phases` (`runtime.cpp:5427`), so an earlier caught failure in a validation-phase shape is NOT a precondition that excludes the route; the argument rests on what actually runs before the route, and on the route itself:
